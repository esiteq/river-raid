# River Raid Clone — інструкції для Claude Code

Це браузерний клон класичної гри **River Raid** (Activision, 1982), написаний
на **Phaser 3** (v3.90.0), максимально наближений до оригіналу за механікою.
Увесь код — vanilla JS + Phaser, без збірки (webpack/vite не потрібні),
без бекенду. Усі спрайти малюються процедурно (без картинок), усі звуки
синтезуються Web Audio API (без аудіофайлів).

Коментарі в коді — українською. Спілкуйся зі мною українською, неформально.

## Структура проєкту

```
index.html        — HTML-каркас, підключає game.css, phaser.min.js, game.js
game.css           — стилі сторінки (центрування canvas, pixelated rendering)
game.js            — ВЕСЬ ігровий код (константи, сцени, логіка) — ОСНОВНИЙ файл для правок
phaser.min.js       — Phaser 3.90.0, взятий з npm-пакету "phaser", не редагувати
assets/             — ОПЦІОНАЛЬНО: вихідні PNG іконок tank/heli/balloon (лише для
                       довідки/майбутнього редагування!) — гра їх НЕ вантажить з диску,
                       вони вбудовані як base64 прямо в game.js (див. нижче)
tests/              — регресійні Playwright-тести (дивись нижче)
package.json        — playwright як devDependency, npm test запускає всі тести
```

Гра відкривається просто через `index.html` у браузері (можна подвійним
кліком, файл:// протокол — ок, зовнішніх залежностей немає). Для тестів
через Playwright зручніше піднімати локальний http-сервер, але file://
теж працює.

### Запуск

```bash
npm install          # підтягне playwright (потрібен лише для тестів)
npx playwright install chromium   # один раз, якщо Chromium ще не стоїть
npm test              # прожене всі регресійні тести в tests/
```

Щоб просто пограти — відкрий `index.html` у браузері, нічого встановлювати
не треба.

## Керування (як в оригіналі)

- `←` / `→` — рух літака вліво/вправо (літак нахиляється "на крило")
- `↑` — газ (пришвидшення скролу)
- `↓` — гальмо (сповільнення скролу, майже до зупинки — потрібно для заправки)
- `SPACE` — постріл / старт гри / рестарт після game over
- `P` або `ESC` — пауза

## Архітектура game.js

Файл лінійний, орієнтовно ~1300+ рядків, ділиться на секції (шукай коментарі
`// ---...---`):

1. **Константи** (верх файлу): розміри поля `W/H`, `ROW_H` (висота рядка
   рельєфу, 8px), швидкості (`MIN_SPEED`, `CRUISE_SPEED`, `BASE_MAX_SPEED`,
   `THROTTLE_ACCEL`), паливо (`FUEL_MAX`, `FUEL_DRAIN_BASE/MAX`,
   `FUEL_REFILL_RATE`), `MISSILE_SPEED`, `INVULN_TIME`, `EXTRA_LIFE_STEP`.
2. **`COL`** — палітра кольорів (hex, як Phaser tint values).
3. **`SFX`** — синтезовані звуки через Web Audio (`tone()`, `shoot()`,
   `explode()`, `fuel()`, `crash()`, `bridge()`, `life()`, `tankShot()`,
   `heliShot()`, `chop()`, `extraLife()`). Нових звуків додавай сюди ж, за
   тим самим патерном.
4. **`generateAllTextures(scene)`** — процедурно "запікає" більшість спрайтів
   у текстури через `scene.add.graphics()` + `generateTexture(key, w, h)`.
   Хелпери всередині: `P(g,px,x,y,w,h,color)` (прямокутник у "пікселях"
   спрайту) і `circ(g,px,cx,cy,r,color)` (коло). Процедурні текстури: `ship`,
   `tankShell`, `heliShell`, `fuel`, `missile`, `explo1/2/3`, `bridgeTile`,
   `bridgeTower`. Щоб додати новий тип ворога чи об'єкта — додай сюди нову
   текстуру за тим самим підходом (малювання прямокутниками/колами в
   невеликій сітці, потім масштабування спрайту через `setScale` при спавні).
   **Виняток:** `tank`, `heli`, `balloon`, `player`, `jet` — це більше НЕ
   процедурна графіка. Вони завантажуються як готові PNG-іконки через
   `BootScene.preload()`, з констант `ASSET_TANK_PNG`/`ASSET_HELI_PNG`/
   `ASSET_BALLOON_PNG`/`ASSET_PLAYER_PNG`/`ASSET_JET_PNG` (`data:` URI,
   base64, оголошені одразу перед `MISSILE_SPEED` на початку файлу).
   Причина вбудовування саме як base64, а не окремих файлів `assets/*.png`:
   Phaser 3.90 вантажить зображення через XHR, а браузери блокують
   XHR-запити до `file://` через CORS — окремі файли ламали гру при
   відкритті подвійним кліком (без сервера). Base64 в самому `game.js` цю
   проблему повністю обходить і не порушує "single-file-per-concern"
   структуру проєкту (`assets/*.png` в репозиторії лишились лише як вихідні
   файли для довідки, гра їх не читає). `tank`/`heli`/`balloon`/`player`
   орієнтовані так само, як і старі процедурні спрайти (дуло танка/ніс
   гелікоптера/ніс гравця — типово вправо/вгору), тож `setFlipX()` для них
   не змінювався. **`jet` — виняток із винятку:** нова картинка за
   замовчуванням "дивиться" вліво (стара процедурна текстура дивилась
   вправо), тож напрямок `setFlipX()` у `spawnEnemy()` для `jet` довелось
   ІНВЕРТУВАТИ відносно старої логіки (`fromLeft ? true : false`, було
   навпаки) — якщо колись знову зʼявиться баг "літак летить хвостом уперед",
   перевір це першим ділом. Розміри відображення контролюються через
   `setScale(TANK_SCALE/HELI_SCALE/BALLOON_SCALE/PLAYER_SCALE/JET_SCALE)`
   (константи одразу під `MISSILE_SPEED`; `PLAYER_TITLE_SCALE` — окремий,
   трохи більший масштаб лише для гравця на тайтл-екрані) — самі PNG
   відрендерені з 3x-суперсемплінгом (наприклад, `player` 135x135,
   `jet` 132x93), тому базовий масштаб 1/3. Текстурам також вручну
   виставлено `Phaser.Textures.FilterMode.LINEAR` у `BootScene.create()` —
   інакше глобальний `pixelArt:true` в конфігу гри дав би грубе
   "сходинкове" масштабування (це не піксель-арт, а плоскі іконки, їм
   потрібне згладжування).
5. **`TerrainGen`** — клас, що генерує рельєф річки рядок за рядком
   (`nextRow(scrollDeltaPx)`): плавний, інерційний (momentum-based) рух
   берегів — `halfWidth`/`centerX` змінюються через `halfVel`/`centerVel`
   (маленькі випадкові поштовхи міняють швидкість, а не саму позицію
   напряму, з м'яким "відбиттям" швидкості при досягненні меж), острови
   (фази grow/hold/shrink), мости (заморожує ширину берегів на час мосту).
   Якщо колись знову з'являться "рвані"/зигзагоподібні береги — перевір,
   чи хтось не замінив цю інерційну модель назад на незалежний
   `Phaser.Math.Between(-2,2)` per-row (так було раніше, і виглядало рвано).
6. **`BootScene`** — завантаження/генерація текстур.
7. **`TitleScene`** — головний екран, легенда бонусів (T/M/D/F/N/X).
8. **`GameScene`** — основний клас гри. `create()` ініціалізує стан,
   `updatePlaying(dt)` — головний ігровий цикл на кожен кадр.

### Модель скролу рельєфу (ВАЖЛИВО, легко зламати)

Рельєф — це масив `this.rows` (індекс 0 = найновіший/найвищий рядок).
Коли `scrollAccum` (накопичений піксельний зсув) перевищує `ROW_H` (8px),
масив зсувається: `this.rows.pop()` (видалити найстаріший знизу) +
`this.rows.unshift(newRow)` (додати новий згори). Формула екранної
Y-координати рядка: **`y = i * ROW_H + this.scrollAccum`** (саме `+`, не
`-` — тут була jitter-помилка, дивись нижче).

Всі інші об'єкти (вороги, паливо, танки, кулі, мости, повітряні кулі) НЕ
прив'язані до дискретних рядків — вони рухаються неперервно:
`entity.y += scrollDelta` щокадру, де `scrollDelta = scrollSpeed * dt`.
Це навмисне рішення, щоб уникнути "сходинкового" тремтіння — не намагайся
"оптимізувати" це назад у прив'язку до рядків.

**Відомий раніше баг**: якщо десь з'явиться формула `y = i * ROW_H -
this.scrollAccum`, це знову викличе тремтіння берегів/мосту (pixel jitter,
sawtooth-патерн). Якщо побачиш дивне сіпання при скролі — перевір знак у
цій формулі першим ділом.

### Швидкість і рівні

- `this.scrollSpeed` — поточна швидкість скролу, змінюється газом/гальмом
  між `this.minSpeed` і `this.maxSpeed`.
- `this.minSpeed` / `this.maxSpeed` — НЕ константи, а властивості сцени,
  бо масштабуються по рівнях: у `advanceLevel()` (викликається при
  проходженні кожного мосту) множаться на `1 + 0.1 * (this.level - 1)`.
  Тобто на рівні 11 (10 мостів пройдено) швидкість рівно вдвічі більша,
  ніж на старті. Якщо міняєш цю логіку — не забудь, що `this.scrollSpeed`
  теж треба підтягувати вгору (`Math.max(this.scrollSpeed, this.minSpeed)`),
  інакше після левел-апу гравець може застрягти нижче нового мінімуму.
- Константи `MIN_SPEED` / `BASE_MAX_SPEED` — це базові (рівень 1) значення,
  самі по собі більше ніде не використовуються напряму в ігровому циклі
  (скрізь `this.minSpeed`/`this.maxSpeed`).
- `CRUISE_SPEED` — швидкість старту/респавну після втрати життя, НЕ
  масштабується по рівнях (свідоме рішення з попереднього запиту).

### Зброя і бонуси

- `this.missiles = []` — масив снарядів (не одиничний об'єкт — рефакторили
  спеціально під мульти-постріли).
- `this.activePower` — `null | 'triple' | 'missile' | 'double'`, активний
  бонус, тримається до підбору іншого бонусу або до краху гравця
  (скидається в `crashPlayer()`).
- Кожен снаряд має поле `normal: boolean` — тільки "звичайні" (прямі вперед)
  постріли можуть збивати/підбирати бонусні повітряні кулі. Спеціальні
  постріли (ракети самонаведення, бічні постріли Triple) і nuke-бонус
  ігнорують кулі (`resolveMissileCollision`, `nukeAllEnemies` — перевір
  умову `m.normal &&` при зміні цієї логіки).
- Бонусні кулі (`spawnBalloon`, `collectBalloon`): пул літер
  `['T','T','M','M','D','D','F','F','N','X']`. F/N/X — миттєва дія (паливо,
  nuke, extra life), не встановлюють `activePower`. T/M/D — встановлюють
  `activePower` і залишаються активними до заміни/краху.
- Ліміт ворогів: не більше 3 одиниць кожного типу (`heli`/`ship`/`jet`)
  одночасно на екрані — перевірка в `spawnEnemy()`.

## Тести (tests/)

Playwright-тести, кожен — окремий `.js`-файл, запускається як звичайний
node-скрипт (не jest/mocha — навмисно просто, без test-runner залежностей).
Кожен тест відкриває `index.html`, симулює клавіатуру, і читає стан гри
напряму через `page.evaluate(() => window.game.scene.keys.Game.<поле>)`.

- `test-smoke.js` — базовий прогін: старт, рух, постріл, пауза, без помилок
  у консолі.
- `test-gameover-restart.js` — 4 краші поспіль → game over → рестарт коректно
  скидає стан.
- `test-bridge-bonus.js` — міст з'являється і руйнується, очки нараховуються.
- `test-bridge-tank-road.js` — танк на мосту: спочатку дорога, потім проліт;
  застрягання й стрільба, якщо міст знищено до того, як танк проїхав; x3
  бонус лише за танк САМЕ на прольоті; чисте втікання без застрягання.
- `test-banking-and-fuel.js` — крен літака при повороті, повне відновлення
  пального після краху.
- `test-speed-scaling.js` — швидкість подвоюється рівно на 10 рівнів.
- `test-tank-drive.js` — береговий танк заїжджає до берега, зупиняється
  перед деревом, стріляє лише "на березі", постріл строго горизонтальний.
- `test-new-features.js` — іконки tank/heli/balloon/player/jet реально
  завантажені й мають очікуваний розмір відображення; `jet` правильно
  дзеркалиться за напрямком польоту (нова картинка за замовчуванням
  "дивиться" вліво, на відміну від старої процедурної текстури); гелікоптер
  стріляє по гравцю і може влучити; дерево/кущ на березі знищується
  пострілом і дає очки; річка згинається сильніше, ніж у старій формулі
  (`centerVel` виходить за межі старого клампу ±1.4).
- `run-all.js` — прожене всі `test-*.js` файли послідовно і виведе підсумок
  (це і є те, що викликає `npm test`).

**Після будь-якої зміни в `game.js` обов'язково прожени `npm test`** і
переконайся, що всі тести зелені, перш ніж вважати задачу виконаною. Якщо
додаєш нову механіку — додай новий `test-*.js` файл за тим самим патерном
(він автоматично підхопиться `run-all.js`, назва просто має починатись з
`test-`).

Якщо тест падає з "browser not found" — виконай
`npx playwright install chromium`.

## Стиль і конвенції

- Коментарі та UI-тексти — українською.
- Немає TypeScript, немає збірки — просто редагуй `game.js` напряму.
- Нові спрайти малюй процедурно в `generateAllTextures()`, за прикладом
  існуючих (маленька сітка "пікселів", потім масштабування) — це й далі
  дефолт. Готові PNG-іконки (як `tank`/`heli`/`balloon`) — свідомий виняток
  на прохання користувача, а не новий загальний підхід; якщо додаєш ще одну
  таку іконку — вбудовуй її як base64 `data:` URI в сам `game.js` (не окремий
  файл в `assets/`), інакше зламаєш запуск через `file://` (див. розділ 4
  вище про `generateAllTextures`).
- Нові звуки — через `SFX`, синтез Web Audio, без аудіофайлів.
- Не редагуй `phaser.min.js` — це сторонній build.

## Історія фіч (що вже реалізовано, щоб не дублювати роботу)

- Базова механіка: скрол рельєфу, острови, мости, паливо, життя, рахунок.
- Кругла анімація вибуху, крен літака при повороті, повне паливо після
  респавну.
- Гелікоптери (реалістичний дизайн), кораблі, реактивні літаки (швидкі,
  не стріляють, летять горизонтально).
- Берегові танки: спавняться на березі, стріляють прямо через річку
  (перпендикулярно, не прицільно по гравцю).
- Танк на мосту: спочатку їде "дорогою" на березі, потім заїжджає на сам
  проліт мосту і перетинає його; якщо встигнути знищити міст, поки танк ще
  на дорозі або на прольоті — очки потроюються, АЛЕ ТІЛЬКИ якщо він вже
  реально був на прольоті (`bridge.tankOnBridge === true`); сам танк при
  цьому НЕ гине, а "застрягає" й стріляє, як звичайний танк на березі
  (детально — нижче, розділ "Танк на мосту: дорога + застрягання").
- Бонусні "ЛГБТ повітряні кулі" (веселкові, з корзиною) з літерами:
  `T` triple-постріл (вперед+вліво+вправо, всі прямі), `M` missile
  (самонаведення з обох боків), `D` double (вдвічі частіші постріли),
  `F` fuel (миттєво 100%), `N` nuke (знищує всіх ворогів на екрані, але НЕ
  кулі), `X` extra life. Бонус діє до підбору іншого або до краху.
- Ліміт 3 вороги кожного типу на екрані одночасно.
- Швидкість рівня зростає на 10% з кожним пройденим мостом (лінійно,
  х2 на рівні 11).
- Береги річки плавні (не рвані): `TerrainGen` рухає `halfWidth`/`centerX`
  через "швидкість" (`halfVel`/`centerVel`, інерція з м'яким відбиттям від
  меж), а не незалежним випадковим кроком щорядка — дивись розділ про
  модель скролу вище.
- Дерева/кущі на берегах: `TerrainGen.nextRow()` кожного рядка окремо для
  лівого й правого берега має лічильник-"кулдаун" (`decoLeftCooldown`/
  `decoRightCooldown`), при досягненні нуля генерує `row.decoLeft`/
  `row.decoRight` (`{tree, inset}`) і скидає кулдаун на випадкове число
  рядків (7-18). Малюються суто декоративно в `drawTerrain()` окремим
  проходом ПІСЛЯ всього суходолу (`GameScene.drawTree`/`drawBush`) —
  важливо малювати їх саме після, інакше рядки землі, намальовані нижче
  по потоку, "затирають" нижню частину дерева/куща. На колізії не
  впливають (перевіряються лише `row.left`/`row.right`).
- Заправки (`fuelTimer`) з'являються вдвічі частіше, ніж у першій версії:
  інтервал 2.75–4.25с замість 5.5–8.5с.
- Ігрове поле на всю висоту екрана: константа `H` більше не хардкод 640,
  а `Phaser.Math.Clamp(window.innerHeight, 640, 1400)` (дивись верх файлу).
  Все інше (`ROWS_COUNT`, `PLAYER_Y`, позиції HUD) вже виражені через `H`
  формулами, тому працює автоматично. Обчислюється один раз при завантаженні
  сторінки (не реагує на подальший resize вікна — це нормально для такого
  типу гри).
- Берегові танки тепер "заїжджають" до берега, а не з'являються одразу на
  ньому:
  - `spawnShoreTank()` стартує танк РІВНО на краю екрана (`x=0` зліва,
    `x=W` справа, залежно від `side`) і зберігає ПРЯМЕ посилання на "свій"
    рядок берега (`t.row = this.rows[3]`, фіксується один раз при спавні).
  - **Важливо:** `updateTanks()` навмисно НЕ шукає рядок через
    `rowAtScreenY(t.y)` щокадру — при від'ємному `y` (танк ще над екраном)
    ця функція клампиться на "поточний" `rows[0]`, який щокадру змінюється
    (нові рядки постійно `unshift`-яться), тож дерево, поставлене на
    "свій" рядок, могло взагалі не збігтися з тим, який танк перевіряє.
    Пряме посилання на об'єкт рядка вирішує це раз і назавжди — `row.left`/
    `row.right`/`row.decoLeft`/`row.decoRight` в ньому незмінні після
    створення.
  - Танк рухається до берега зі швидкістю `DRIVE_SPEED = 60` px/сек
    (`updateTanks()`). Якщо на "своєму" рядку є `decoLeft`/`decoRight` з
    `tree: true` і воно розташоване між краєм екрана і берегом (перевірка
    `treeX < bankX` для лівого боку / `treeX > bankX` для правого) — танк
    зупиняється за `TREE_CLEARANCE = 20` px до дерева і залишається там
    назавжди (кущі, `tree: false`, не блокують).
  - Стріляє (`fireTimer` рахується) ЛИШЕ коли `t.atBank === true`, тобто
    реально дістався справжньої лінії берега (`Math.abs(t.x - bankX) < 1`),
    а не зупинився перед деревом.
  - Постріли танків (`fireTankShell`) завжди суто горизонтальні: `vy: 0`,
    і `updateTankBullets()` не додає до `.y` жодного скролу — жодних
    відхилень немає й не повинно з'являтися.
- Текст програшу — `'ГРА ВСЬО'` (`GameScene.gameOver()`), НЕ "GAME OVER".
  Саме така форма (з великої, без крапки) — так просив користувач, не
  "виправляй" на англійський варіант.
- **Танк на мосту: дорога + застрягання.** `spawnBridgeVisual()` тепер
  стартує танк не на самому мосту, а на "дорозі" перед ним:
  `bridge.tankStartX` = позиція за `ROAD_LEN = 90` px до краю мосту
  (обрізана краєм екрана, якщо берег вузький), `bridge.tankEndX` —
  протилежний край прольоту, як і раніше. Рух — той самий
  `Phaser.Math.Linear(startX, endX, tankProgress)` на всю відстань
  (дорога + міст), швидкість `bridge.tankSpeed = 70` px/сек (піднята з 42,
  бо відстань зросла — інакше на високих рівнях танк не встигає доїхати
  до того, як усе проскролить за межі екрана).
  `bridge.tankOnBridge` (обчислюється щокадру в `updateBridgeVisuals()`
  як `x >= bridge.left`/`x <= bridge.right` залежно від напрямку)
  відрізняє фазу "ще їде дорогою" від "вже на прольоті" — це і є критерій
  для x3-бонусу.
  Якщо гравець влучає по мосту (`resolveMissileCollision()`, гілка
  "влучання по мосту") ПОКИ `bridge.tankAlive` ще true (танк не встиг
  втекти) — раніше танк просто вибухав разом з мостом; ТЕПЕР замість
  цього викликається `strandBridgeTank(bridge)`, яка перетворює його на
  звичайний запис у `this.tanks[]` (той самий масив, що й берегові танки):
  `row: null` (нікуди більше не їде — вже "запаркований"), `atBank: true`
  (стріляє одразу, щойно спрацює `fireTimer`), `side` виставляється так,
  щоб стріляти в напрямку, в якому він рухався (`tankDir === 1 → 'left'`,
  бо `side:'left'` в `fireTankShell()` означає постріл ВПРАВО). Завдяки
  цьому вся логіка стрільби/колізій/видалення застряглого танка — це та
  сама логіка, що й для звичайних берегових танків, без дублювання коду.
  `updateBridgeVisuals()` має свою власну (резервну) перевірку
  `if (!bridge.alive) this.strandBridgeTank(bridge)` на наступний кадр —
  це підстраховка на випадок, якщо колись з'явиться інший шлях знищення
  мосту, що не проходить через `resolveMissileCollision()`.
  **Важливо:** через це `updateTanks()` більше не може покладатись, що в
  усіх записів `this.tanks[]` є `t.row` — синхронізація `t.img.x/img.y`
  винесена ЗА межі `if (t.row) {...}` блоку (раніше застряглий танк без
  `row` мав "заморожений" спрайт, бо позиція оновлювалась лише всередині
  того блоку).

- **Готові іконки замість трьох процедурних спрайтів.** `tank`, `heli`,
  `balloon` тепер — реальні PNG-картинки (плоскі "емоджі-стиль" іконки),
  завантажені як base64 `data:` URI (детально — розділ 4 вище). Орієнтація
  збігається зі старими спрайтами (дуло/ніс — вправо за замовчуванням), тож
  `setFlipX()` в `spawnShoreTank()`, `spawnBridgeVisual()` та `updateEnemies()`
  (heli) не змінювались. Розміри відображення: танк ~48x24, гелікоптер
  ~55x30, куля ~28x40 (`TANK_SCALE`/`HELI_SCALE`/`BALLOON_SCALE`, кожен раз
  множаться на додатковий коефіцієнт там, де раніше був окремий `setScale`,
  напр. міст-танк ×1.1, кулька на тайтлі ×1.6). Хітбокси колізій (`resolveMissileCollision`,
  `checkPlayerCollisions`) навмисно НЕ чіпались — лишились ті самі
  hard-coded числа, що й раніше, для балансу.
- **Гелікоптер тепер стріляє по гравцю** (як в оригінальній River Raid,
  раніше — тільки літав хвилею вліво-вправо). `spawnEnemy()` для `type ===
  'heli'` додає `enemy.fireTimer`; в `updateEnemies()`, поки гелікоптер
  видно на екрані (`e.y > 6 && e.y < H - 10`), таймер рахується і при нулі
  викликає `fireHeliShell(e)` — приціл береться ОДИН РАЗ у момент пострілу
  (вектор від гелікоптера до поточної позиції `this.player`), снаряд далі
  летить по прямій без самонаведення. Снаряди — окремий масив
  `this.heliBullets[]` (не переплутуй з `this.tankBullets[]` — різні
  джерела, різна траєкторія: танкові строго горизонтальні, гелікоптерні —
  під довільним кутом), окрема текстура `heliShell` (червона, щоб відрізнялась
  від оранжевого танкового пострілу), `updateHeliBullets(dt)` викликається в
  `updatePlaying()` поруч з `updateTankBullets(dt)`. `nukeAllEnemies()`
  тепер прибирає й `heliBullets`, що вже в польоті.
- **Дерева/кущі на березі стали знищуваними.** Раніше `row.decoLeft`/
  `row.decoRight` (`{tree, inset}`) були суто декоративними — малювались у
  `drawTerrain()`, але жодних колізій не мали. Тепер `resolveMissileCollision(m)`
  додатково перебирає `this.rows` (та сама формула екранної Y, що й у
  `drawTerrain()`/`rowAtScreenY()`: `y = i*ROW_H + this.scrollAccum`) і за
  влучання викликає `destroyDeco(row, 'decoLeft'|'decoRight', x, y)` —
  прибирає об'єкт з рядка (`row[key] = null`, тому `drawTerrain()` більше
  його не малює), дає очки (дерево 30, кущ 15) і невеликий вибух+звук
  (`SFX.chop()`). Побічний ефект (навмисний, реалістичний): якщо береговий
  танк був заблокований цим деревом (`updateTanks()`), після його знищення
  танк наступного кадру продовжить їхати до берега, бо перевіряє
  `row.decoLeft`/`row.decoRight` щокадру, а не одноразово при спавні.
- **Річка згинається помітно сильніше.** `TerrainGen.nextRow()`: амплітуда
  випадкового поштовху `centerVel` піднята з `FloatBetween(-0.3, 0.3)` до
  `FloatBetween(-0.55, 0.55)`, а межа (clamp) — з `±1.4` до `±2.6`. `halfVel`
  (ширина річки) не чіпали — саме "пряма лінія" центру була основною
  скаргою, ширина й так плавно "дихала". Якщо знадобиться ще плавніше/різкіше
  — крутити саме ці два числа в `nextRow()`, вони прямо на початку методу.

- **Готові іконки для гравця і "бічного" реактивного літака.** `player`
  (літак гравця, на тайтл-екрані й у грі) і `jet` (ворожий літак, летить
  горизонтально) — за тим самим принципом, що й `tank`/`heli`/`balloon`
  вище: base64 `data:` URI в `ASSET_PLAYER_PNG`/`ASSET_JET_PNG`,
  `PLAYER_SCALE ≈ 1/3` (→ ~45x45 у грі), `PLAYER_TITLE_SCALE ≈ 0.71`
  (→ ~96x96 на тайтл-екрані, окремий, трохи більший масштаб — раніше теж
  був окремий `setScale(3)` проти `setScale(1.4)` в грі), `JET_SCALE ≈ 1/3`
  (→ ~44x31). Player-картинка — квадратна (1:1), симетрична, "дивиться"
  вгору за замовчуванням, як і стара текстура — жодних змін у логіці крену
  (`this.player.angle`) не знадобилось, вона просто крутить сам image.
  **Важлива відмінність від tank/heli/balloon:** нова картинка `jet` за
  замовчуванням "дивиться" ВЛІВО, тоді як стара процедурна текстура
  дивилась ВПРАВО — тож у `spawnEnemy()` напрямок `img.setFlipX(...)` для
  `jet` довелось інвертувати (`fromLeft` тепер дає `flipX=true`, було
  `flipX=false`), інакше літак летів би хвостом уперед. Хітбокси
  (`resolveMissileCollision`/`checkPlayerCollisions`, hw для jet=20/18)
  так само НЕ чіпались, як і для попередньої трійки іконок.

## Changelog

Кожну зміну гри (фічу, фікс, баланс) — записуй у [`CHANGELOG.md`](./CHANGELOG.md)
(найновіше зверху, коротким описом що і чому). Онови його в тому ж коміті,
де й сама зміна коду — не залишай на "потім".

## Наступні кроки / формат роботи

Коли я прошу нову фічу чи фікс:
1. Зроби зміну в `game.js` (і `game.css`/`index.html`, якщо треба).
2. Прожени `npm test` — усі тести мають бути зеленими.
3. Якщо додав нову механіку — додай тест під неї.
4. Додай запис у `CHANGELOG.md` (найновіше зверху).
5. Коротко опиши, що змінилось, українською.

Гру НЕ потрібно знову "зшивати" в один HTML-файл — тримаємо `index.html`,
`game.css`, `game.js`, `phaser.min.js` окремими файлами.
