# River Raid Clone — інструкції для Claude Code

Це браузерний клон класичної гри **River Raid** (Activision, 1982), написаний
на **Phaser 3** (v3.90.0), максимально наближений до оригіналу за механікою.
Увесь код — vanilla JS + Phaser, без збірки (webpack/vite не потрібні),
без бекенду. Більшість спрайтів малюється процедурно кодом; кілька ключових
іконок (танк, гелікоптер, гравець, реактивний літак, корабель, заправка,
куля-бонус, вибух, дерева й кущі на березі) — готові PNG-картинки з
`assets/` (див. нижче чому саме так). Усі звуки синтезуються Web Audio API
(без аудіофайлів).

Коментарі в коді — українською. Спілкуйся зі мною українською, неформально.

## Структура проєкту

```
index.html        — HTML-каркас, підключає game.css, phaser.min.js, game.js
game.css           — стилі сторінки (центрування canvas, pixelated rendering)
game.js            — ВЕСЬ ігровий код (константи, сцени, логіка) — ОСНОВНИЙ файл для правок
phaser.min.js       — Phaser 3.90.0, взятий з npm-пакету "phaser", не редагувати
assets/             — ОБОВ'ЯЗКОВІ PNG-іконки (tank/heli/balloon/player/jet/ship/
                       fuel/explo/tree1/tree2/bush1/bush2), гра вантажить їх з
                       диску через this.load.image() — БЕЗ них гра не
                       запуститься. Кожен файл заздалегідь відмасштабований
                       рівно до розміру, який гра реально показує (без зайвої
                       "ваги про запас")
serve.js            — мінімальний http-сервер без залежностей, `npm start`
tests/              — регресійні Playwright-тести (дивись нижче), включно з
                       tests/serve.js — тим самим сервером для тестів
package.json        — playwright як devDependency; npm start підіймає гру,
                       npm test запускає всі тести
```

**ВАЖЛИВО (свідома зміна, не забудь):** гра БІЛЬШЕ НЕ відкривається простим
подвійним кліком по `index.html` (`file://`)! Іконки з `assets/` вантажаться
через `this.load.image()`, а Phaser робить це через XHR — браузери
блокують XHR-запити до `file://`. Тому для гри (і для тестів) ОБОВ'ЯЗКОВО
потрібен локальний http-сервер. Якщо після зміни коду гра "не бачить"
картинки або консоль показує CORS/XHR-помилки — це НЕ баг у коді, а
найімовірніше хтось відкрив `index.html` напряму як `file://` замість
`http://localhost:.../`.

### Запуск

```bash
npm install          # підтягне playwright (потрібен лише для тестів)
npx playwright install chromium   # один раз, якщо Chromium ще не стоїть
npm start             # піднімає гру на http://localhost:8080/
npm test              # прожене всі регресійні тести в tests/
```

Щоб просто пограти — `npm start` (або будь-який інший статичний http-сервер,
наприклад `npx http-server` чи `python3 -m http.server`), відкрий адресу, яку
він виведе, у браузері.

## Керування (як в оригіналі)

- `←` / `→` — рух літака вліво/вправо (літак нахиляється "на крило")
- `↑` — газ (пришвидшення скролу)
- `↓` — гальмо (сповільнення скролу, майже до зупинки — потрібно для заправки)
- `SPACE` — постріл / старт гри / рестарт після game over
- `P` або `ESC` — пауза

## Архітектура game.js

Файл лінійний, орієнтовно ~1300+ рядків, ділиться на секції (шукай коментарі
`// ---...---`):

1. **Константи** (верх файлу): розміри поля `W/H`, `ROW_H` (висота рядка
   рельєфу, 8px), швидкості (`MIN_SPEED`, `CRUISE_SPEED`, `BASE_MAX_SPEED`,
   `THROTTLE_ACCEL`), паливо (`FUEL_MAX`, `FUEL_DRAIN_BASE/MAX`,
   `FUEL_REFILL_RATE`), `MISSILE_SPEED`, `INVULN_TIME`, `EXTRA_LIFE_STEP`.
2. **`COL`** — палітра кольорів (hex, як Phaser tint values).
3. **`SFX`** — синтезовані звуки через Web Audio (`tone()`, `shoot()`,
   `explode()`, `fuel()`, `crash()`, `bridge()`, `life()`, `tankShot()`,
   `heliShot()`, `chop()`, `extraLife()`). Нових звуків додавай сюди ж, за
   тим самим патерном.
4. **`generateAllTextures(scene)`** — процедурно "запікає" частину спрайтів
   у текстури через `scene.add.graphics()` + `generateTexture(key, w, h)`.
   Хелпери всередині: `P(g,px,x,y,w,h,color)` (прямокутник у "пікселях"
   спрайту) і `circ(g,px,cx,cy,r,color)` (коло). Процедурні текстури:
   `tankShell`, `heliShell`, `missile`, `bridgeTile`, `bridgeTower`. Щоб
   додати новий тип ворога чи об'єкта — додай сюди нову текстуру за тим
   самим підходом (малювання прямокутниками/колами в невеликій сітці, потім
   масштабування спрайту через `setScale` при спавні).
   **Виняток:** `tank`, `heli`, `balloon`, `player`, `jet`, `ship`, `fuel`,
   `explo`, `tree1`, `tree2`, `bush1`, `bush2`, `homingMissile` — це НЕ
   процедурна графіка.
   Вони завантажуються як готові PNG-файли з диску через
   `this.load.image(key, 'assets/xxx.png')` у `BootScene.preload()`, і в
   `create()` кожній з них додатково виставляється
   `Phaser.Textures.FilterMode.LINEAR` — інакше глобальний `pixelArt:true` в
   конфігу гри дав би грубе "сходинкове" масштабування (це не піксель-арт, а
   плоскі іконки, їм потрібне згладжування).
   **Важлива архітектурна зміна (було: base64 в `game.js`, стало: окремі
   файли в `assets/`):** раніше ці ж іконки вантажились як base64 `data:`
   URI, вбудовані прямо в константи на початку `game.js` — саме так
   обходили те, що Phaser вантажить зображення через XHR, а браузери
   блокують XHR-запити до `file://` через CORS (тобто окремі файли ламали
   запуск подвійним кліком без сервера). Це свідомо змінено: тепер кожен
   PNG заздалегідь відмасштабований (Python/PIL, LANCZOS) РІВНО до розміру,
   який гра реально показує (без "суперсемплінгу про запас", яким
   рятувались раніше) і лежить окремим файлом в `assets/` — разом усі 8
   іконок важать ~50 КБ замість колишніх 100+ КБ роздутого base64-тексту
   в самому `game.js`. **Ціна цього рішення, прийнята свідомо:** гра
   БІЛЬШЕ НЕ відкривається простим подвійним кліком по `index.html`
   (`file://`) — обов'язково потрібен http-сервер (`npm start` або будь-який
   інший), і для гри, і для тестів. Якщо колись знадобиться повернути
   `file://`-сумісність — доведеться або повернутись до base64, або чекати
   на CORS-дозволи від браузерів, третього варіанту з окремими файлами
   немає.
   `tank`/`heli`/`balloon`/`player` орієнтовані так само, як і старі
   процедурні спрайти (дуло танка/ніс гелікоптера/ніс гравця — типово
   вправо/вгору), тож `setFlipX()` для них не змінювався. **`jet` —
   виняток із винятку:** картинка за замовчуванням "дивиться" вліво (стара
   процедурна текстура дивилась вправо), тож напрямок `setFlipX()` у
   `spawnEnemy()` для `jet` довелось ІНВЕРТУВАТИ відносно старої логіки
   (`fromLeft ? true : false`, було навпаки) — якщо колись знову зʼявиться
   баг "літак летить хвостом уперед", перевір це першим ділом. Розміри
   відображення контролюються через `setScale(TANK_SCALE/HELI_SCALE/
   BALLOON_SCALE/PLAYER_SCALE/JET_SCALE/SHIP_SCALE/FUEL_SCALE)` (константи
   одразу під `MISSILE_SPEED`; `PLAYER_TITLE_SCALE` — окремий, трохи більший
   масштаб лише для гравця на тайтл-екрані) — оскільки самі PNG вже
   відмасштабовані рівно під потрібний розмір, ці константи тепер близькі
   до 1 (напр. `TANK_SCALE = 48/53`, `HELI_SCALE = 1`), а не 1/3, як було за
   часів суперсемплінгу. **Заправка (`fuel`):** окремий текстовий напис
   `"FUEL"` над іконкою, який раніше малювався поруч (`this.add.text(...)`),
   прибрано повністю — іконка бочки й так однозначно впізнавана. Через це
   `this.fuels[]` більше НЕ має поля `label` (було `{img, label, x, y,
   alive}`, стало `{img, x, y, alive}`) — якщо десь у коді знову з'явиться
   `f.label`, це або стара копіпаста, або хтось намагається повернути напис
   назад. **Вибух (`explo`):** раніше — три окремі процедурні текстури
   `explo1/2/3`, які підмінялись одна одною для ефекту "росту" (кругла
   анімація). Тепер — одна PNG-іконка, а "ріст/зменшення + обертання"
   робить не зміна текстури, а `spawnExplosion()`/`updateExplosions()`
   через `setScale()`/`.angle` (деталі — нижче, розділ "Історія фіч").
5. **`TerrainGen`** — клас, що генерує рельєф річки рядок за рядком
   (`nextRow(scrollDeltaPx)`): плавний, інерційний (momentum-based) рух
   берегів — `halfWidth`/`centerX` змінюються через `halfVel`/`centerVel`
   (маленькі випадкові поштовхи міняють швидкість, а не саму позицію
   напряму, з м'яким "відбиттям" швидкості при досягненні меж), острови
   (фази grow/hold/shrink), мости (заморожує ширину берегів на час мосту).
   Якщо колись знову з'являться "рвані"/зигзагоподібні береги — перевір,
   чи хтось не замінив цю інерційну модель назад на незалежний
   `Phaser.Math.Between(-2,2)` per-row (так було раніше, і виглядало рвано).
6. **`BootScene`** — завантаження/генерація текстур.
7. **`TitleScene`** — головний екран, легенда бонусів (T/M/D/F/N/X). Усі
   елементи розташовані фіксованими Y-координатами зверху вниз (заголовок →
   картинка літака → блок керування → мета гри → легенда бонусів → кнопка
   старту → версія) — **якщо додаєш новий елемент на цей екран, перевір,
   що його Y-діапазон не перетинається із сусідами** (найпростіше —
   `object.getBounds()` і порівняти top/bottom/left/right, як робить тест
   `test-new-features.js`, пункт 11). Колись блок керування наїжджав прямо
   на картинку літака (`player`) — саме тому тепер є explicit-тест на це,
   не покладайся тільки на "на око". Кнопка старту — `'НАТИСНІТЬ ПРОБІЛ ДЛЯ
   ПОЧАТКУ'` (не англійська `PRESS SPACE TO START`, свідомо перекладено).
   Під нею — рядок версії `` `v${GAME_VERSION} by Alex Raven` ``;
   `GAME_VERSION` — константа на самому початку `game.js` (одразу перед
   `W`) — онови її разом із новим записом у `CHANGELOG.md` при наступній
   помітній зміні, щоб версія на тайтл-екрані не відставала від реальності.
8. **`GameScene`** — основний клас гри. `create()` ініціалізує стан,
   `updatePlaying(dt)` — головний ігровий цикл на кожен кадр.

### Модель скролу рельєфу (ВАЖЛИВО, легко зламати)

Рельєф — це масив `this.rows` (індекс 0 = найновіший/найвищий рядок).
Коли `scrollAccum` (накопичений піксельний зсув) перевищує `ROW_H` (8px),
масив зсувається: `this.rows.pop()` (видалити найстаріший знизу) +
`this.rows.unshift(newRow)` (додати новий згори). Формула екранної
Y-координати рядка: **`y = i * ROW_H + this.scrollAccum`** (саме `+`, не
`-` — тут була jitter-помилка, дивись нижче).

Всі інші об'єкти (вороги, паливо, танки, кулі, мости, повітряні кулі) НЕ
прив'язані до дискретних рядків — вони рухаються неперервно:
`entity.y += scrollDelta` щокадру, де `scrollDelta = scrollSpeed * dt`.
Це навмисне рішення, щоб уникнути "сходинкового" тремтіння — не намагайся
"оптимізувати" це назад у прив'язку до рядків.

**Відомий раніше баг**: якщо десь з'явиться формула `y = i * ROW_H -
this.scrollAccum`, це знову викличе тремтіння берегів/мосту (pixel jitter,
sawtooth-патерн). Якщо побачиш дивне сіпання при скролі — перевір знак у
цій формулі першим ділом.

### Швидкість і рівні

- `this.scrollSpeed` — поточна швидкість скролу, змінюється газом/гальмом
  між `this.minSpeed` і `this.maxSpeed`.
- `this.minSpeed` / `this.maxSpeed` — НЕ константи, а властивості сцени,
  бо масштабуються по рівнях: у `advanceLevel()` (викликається при
  проходженні кожного мосту) множаться на `1 + 0.1 * (this.level - 1)`.
  Тобто на рівні 11 (10 мостів пройдено) швидкість рівно вдвічі більша,
  ніж на старті. Якщо міняєш цю логіку — не забудь, що `this.scrollSpeed`
  теж треба підтягувати вгору (`Math.max(this.scrollSpeed, this.minSpeed)`),
  інакше після левел-апу гравець може застрягти нижче нового мінімуму.
- Константи `MIN_SPEED` / `BASE_MAX_SPEED` — це базові (рівень 1) значення,
  самі по собі більше ніде не використовуються напряму в ігровому циклі
  (скрізь `this.minSpeed`/`this.maxSpeed`).
- `CRUISE_SPEED` — швидкість старту/респавну після втрати життя, НЕ
  масштабується по рівнях (свідоме рішення з попереднього запиту).

### Зброя і бонуси

- `this.missiles = []` — масив снарядів (не одиничний об'єкт — рефакторили
  спеціально під мульти-постріли).
- `this.activePower` — `null | 'triple' | 'missile' | 'double'`, активний
  бонус, тримається до підбору іншого бонусу або до краху гравця
  (скидається в `crashPlayer()`).
- Кожен снаряд має поле `normal: boolean` — тільки "звичайні" (прямі вперед)
  постріли можуть збивати/підбирати бонусні повітряні кулі. Спеціальні
  постріли (ракети самонаведення, бічні постріли Triple) і nuke-бонус
  ігнорують кулі (`resolveMissileCollision`, `nukeAllEnemies` — перевір
  умову `m.normal &&` при зміні цієї логіки).
- Бонусні кулі (`spawnBalloon`, `collectBalloon`): пул літер
  `['T','T','M','M','D','D','F','F','N','X']`. F/N/X — миттєва дія (паливо,
  nuke, extra life), не встановлюють `activePower`. T/M/D — встановлюють
  `activePower` і залишаються активними до заміни/краху.
- **`M` (HOMING) — єдиний бонус з лічильником.** `this.homingCount` —
  скільки самонавідних пострілів лишилось; актуальне лише поки
  `this.activePower === 'missile'`. `collectBalloon()` для `'M'`: якщо ВЖЕ
  `activePower === 'missile'` і `homingCount > 0` — додає `HOMING_BONUS_AMOUNT`
  (50) ЗВЕРХУ наявної кількості; інакше (перший підбір або лічильник щойно
  дійшов до нуля) — перезаписує на `HOMING_BONUS_AMOUNT` з нуля.
  `handleShooting()` у гілці `'missile'` зменшує `homingCount` на 1 ЗА
  ВЕСЬ ПОСТРІЛ (не за кожну з двох ракет окремо, хоч їх і випускається дві —
  одна вліво, одна вправо), і коли лічильник доходить до 0 — сам скидає
  `activePower = null`, тож наступний постріл автоматично стає звичайним
  одиночним (`else`-гілка `handleShooting()`), без жодної додаткової умови в
  HUD чи деінде. HUD (`updateHUD()`) для `'missile'` показує не статичний
  напис, а `` `HOMING ★ ${this.homingCount}` `` — саме тут і тільки тут
  лічильник видно гравцю. `crashPlayer()` скидає `homingCount = 0` разом з
  `activePower = null` (той самий рядок коду, де й активний бонус завжди
  скидався). Спрайт самої ракети — `spawnHomingMissile()` малює
  `'homingMissile'` (готова PNG-іконка, 6x32, `HOMING_MISSILE_SCALE = 1`),
  а НЕ `'missile'` (звичайний/потрійний постріл і далі малюються
  процедурною текстурою `missile` — заміна свідомо торкнулась лише
  самонавідних ракет, `spawnMissile()` не чіпали). Ніс іконки дивиться
  вгору за замовчуванням, так само як і стара процедурна `missile`, тож
  формула `img.rotation = Math.atan2(vy, vx) + Math.PI / 2` (і тут, і в
  `updateMissiles()` для самонаведення в польоті) не змінювалась.
- Ліміт ворогів: не більше 3 одиниць кожного типу (`heli`/`ship`/`jet`)
  одночасно на екрані — перевірка в `spawnEnemy()`.

### Хітбокси по масці PNG (`pixelHit`, `SPRITE_MASKS`)

Раніше (і досі для decoLeft/decoRight до відповідної фічі) влучання
пострілу перевірялось прямокутником "на око" (`Math.abs(mx-e.x) < hw &&
Math.abs(my-e.y) < hh`). Для готових PNG-іконок це давало "перекошене"
відчуття — асиметричні картинки (щогла корабля, лопаті гелікоптера) мають
багато прозорих пікселів у куточках bounding box, і постріл повз видиму
картинку, але всередині прямокутника, зараховувався як влучання.

Тепер для іконок, по яких перевіряється влучання (`tank`, `heli`, `ship`,
`jet`, `fuel`, `balloon`, `tree1`, `tree2`, `bush1`, `bush2`), хітбокс — це
реальні непрозорі пікселі самої картинки:

- `SPRITE_MASKS` (module-level `const`, одразу перед `BootScene`) —
  `{ textureKey: { width, height, alpha: Uint8ClampedArray } }`, лише альфа-
  канал кожного пікселя (0-255).
- `buildSpriteMask(scene, key)` — будує маску ОДИН РАЗ: малює текстуру на
  тимчасовий `<canvas>`, читає `getImageData().data`, копіює лише альфа-байти.
  Викликається в `BootScene.create()` для списку ключів одразу після циклу,
  що виставляє `LINEAR`-фільтр (окремий, коротший список — маска потрібна
  тільки тим текстурам, по яких реально перевіряється влучання; `player`
  (по ньому ніхто не стріляє) і `explo` (косметика) в цей список НЕ входять).
- `pixelHit(img, worldX, worldY)` — чи є непрозорий піксель картинки `img`
  (Phaser.Image) у світовій точці? Переводить світову точку в локальні
  координати текстури з урахуванням позиції, кута (`img.angle`), масштабу
  (`img.scaleX/scaleY`) і дзеркалення (`img.flipX/flipY`) — тобто хітбокс
  ЗАВЖДИ синхронний з тим, що реально намальовано на екрані просто зараз, а
  не статична "коробка" з фіксованими hw/hh. Поріг `alpha > 20` відсікає
  майже прозорі краї (згладжування).
- Використовується в `resolveMissileCollision()` замість усіх старих
  `Math.abs(mx-x) < hw`-перевірок для ворогів/заправки/танків/дерев-кущів/
  куль-бонусів/танка на мосту. Влучання по самому мосту (геометрична
  перевірка діапазону x, не PNG) і колізії гравця з берегом/ворогом
  (`checkPlayerCollisions`) НЕ чіпались — лишились старими прямокутниковими
  перевірками (поза скоупом цієї зміни).
- **Якщо додаєш нову PNG-іконку, по якій гравець зможе стріляти** — додай
  її ключ до списку `buildSpriteMask()`-виклику в `BootScene.create()`,
  інакше `pixelHit()` для неї завжди повертатиме `false` (немає маски →
  "промах", а не помилка) і по ній ніколи не можна буде влучити.

## Тести (tests/)

Playwright-тести, кожен — окремий `.js`-файл, запускається як звичайний
node-скрипт (не jest/mocha — навмисно просто, без test-runner залежностей).
Кожен тест відкриває `index.html`, симулює клавіатуру, і читає стан гри
напряму через `page.evaluate(() => window.game.scene.keys.Game.<поле>)`.

**Тести відкривають сторінку через http, НЕ через `file://`.** Причина та
сама, що й для самої гри (іконки з `assets/` вантажаться через XHR, а
`file://` браузер блокує) — тому кожен тест на старті сам піднімає
локальний сервер через `startServer()` з `tests/serve.js` (той самий
мінімальний http-сервер без залежностей, що й кореневий `serve.js`, тільки
слухає рандомний вільний порт: `server.listen(0, '127.0.0.1', ...)`) і в
кінці викликає `server.close()`. Якщо пишеш новий тест — копіюй цей патерн
з будь-якого існуючого файлу (`const { startServer } = require('./serve');`
→ `const { server, url } = await startServer(path.join(__dirname, '..'));`
→ `page.goto(url + 'index.html')` → в кінці `server.close();`), а не
хардкодь `'file://' + path.join(...)`, як робилось у старих версіях
тестів — воно просто не запрацює.

- `test-smoke.js` — базовий прогін: старт, рух, постріл, пауза, без помилок
  у консолі.
- `test-gameover-restart.js` — 4 краші поспіль → game over → рестарт коректно
  скидає стан.
- `test-bridge-bonus.js` — міст з'являється і руйнується, очки нараховуються.
- `test-bridge-tank-road.js` — танк на мосту: спочатку дорога, потім проліт;
  застрягання й стрільба, якщо міст знищено до того, як танк проїхав; x3
  бонус лише за танк САМЕ на прольоті; чисте втікання без застрягання.
- `test-banking-and-fuel.js` — крен літака при повороті, повне відновлення
  пального після краху.
- `test-speed-scaling.js` — швидкість подвоюється рівно на 10 рівнів.
- `test-tank-drive.js` — береговий танк заїжджає до берега, зупиняється
  перед деревом, стріляє лише "на березі", постріл строго горизонтальний.
- `test-new-features.js` — іконки tank/heli/balloon/player/jet/ship/fuel
  реально завантажені й мають очікуваний розмір відображення; `jet`
  правильно дзеркалиться за напрямком польоту (нова картинка за
  замовчуванням "дивиться" вліво, на відміну від старої процедурної
  текстури); заправка більше НЕ має текстового напису `"FUEL"`; гелікоптер
  стріляє по гравцю СУВОРО горизонтально (`vy === 0`) і може влучити;
  дерево/кущ на березі знищується пострілом і дає очки; дерева/кущі
  спавняться як `Image`-об'єкти з правильною текстурою за типом/варіантом
  (`spawnDecoImages`), рухаються зі скролом (`updateDecoImages`) і
  знищуються і пострілом (`destroyDeco`), і при вислизанні рядка за нижній
  край масиву (`destroyRowDecoImages`); річка згинається сильніше, ніж у
  старій формулі (`centerVel` виходить за межі старого клампу ±1.4);
  HOMING-бонус (`M`) стартує з 50, зменшується на 1 за постріл (не за кожну
  з двох ракет), стекається при повторному підборі (не перезаписує), сам
  вимикається при 0 (наступний постріл — звичайний), і HUD показує саме
  поточне число (`HOMING ★ 47`), а сама самонавідна ракета використовує
  готову іконку `'homingMissile'` (6x32) — постріли симулюються напряму
  через `s.keys.SPACE._justDown = true; s.handleShooting();` замість
  реальних DOM keyboard-подій (детерміновано й миттєво, без очікування
  польоту ракети);
  хітбокс тепер по масці PNG (`pixelHit`) — постріл у прозорий кут іконки не
  влучає, у непрозору точку влучає, з урахуванням масштабу й дзеркалення
  (перевірка звіряється з реальними даними `SPRITE_MASKS`, а не з
  захардкодженими припущеннями про конкретну картинку); тайтл-екран —
  картинка гравця і текст керування НЕ перетинаються (`getBounds()`), кнопка
  старту й рядок версії мають очікуваний текст (перевіряється ДО першого
  натискання SPACE, поки ще активна `Title`-сцена, через окремий
  `waitForTitleScene()`, а не `waitForGameScene()`).
- `run-all.js` — прожене всі `test-*.js` файли послідовно і виведе підсумок
  (це і є те, що викликає `npm test`).

**Після будь-якої зміни в `game.js` обов'язково прожени `npm test`** і
переконайся, що всі тести зелені, перш ніж вважати задачу виконаною. Якщо
додаєш нову механіку — додай новий `test-*.js` файл за тим самим патерном
(він автоматично підхопиться `run-all.js`, назва просто має починатись з
`test-`).

Якщо тест падає з "browser not found" — виконай
`npx playwright install chromium`.

## Стиль і конвенції

- Коментарі та UI-тексти — українською.
- Немає TypeScript, немає збірки — просто редагуй `game.js` напряму.
- Нові спрайти малюй процедурно в `generateAllTextures()`, за прикладом
  існуючих (маленька сітка "пікселів", потім масштабування) — це й далі
  дефолт. Готові PNG-іконки (як `tank`/`heli`/`balloon`/`explo`) — свідомий
  виняток на прохання користувача, а не новий загальний підхід; якщо
  додаєш ще одну таку іконку:
  1. Заздалегідь відмасштабуй PNG (Python/PIL, LANCZOS) РІВНО до розміру,
     який гра реально показуватиме — без "про запас"/суперсемплінгу, щоб
     не роздувати `assets/` зайвими кілобайтами.
  2. Поклади готовий файл у `assets/новаіконка.png`.
  3. Завантаж через `this.load.image('key', 'assets/новаіконка.png')` у
     `BootScene.preload()` і додай `'key'` у список, якому в `create()`
     виставляється `Phaser.Textures.FilterMode.LINEAR`.
  **НЕ вбудовуй нові іконки як base64 в `game.js`** — так робили раніше
  (заради сумісності з `file://`), але від цього підходу свідомо відмовились
  на користь окремих файлів у `assets/` (менший `game.js`, менша загальна
  вага) — деталі й компроміс (більше немає `file://`) описані в розділі 4
  вище про `generateAllTextures`.
- Нові звуки — через `SFX`, синтез Web Audio, без аудіофайлів.
- Не редагуй `phaser.min.js` — це сторонній build.

## Історія фіч (що вже реалізовано, щоб не дублювати роботу)

- Базова механіка: скрол рельєфу, острови, мости, паливо, життя, рахунок.
- Кругла анімація вибуху, крен літака при повороті, повне паливо після
  респавну.
- Гелікоптери (реалістичний дизайн), кораблі, реактивні літаки (швидкі,
  не стріляють, летять горизонтально).
- Берегові танки: спавняться на березі, стріляють прямо через річку
  (перпендикулярно, не прицільно по гравцю).
- Танк на мосту: спочатку їде "дорогою" на березі, потім заїжджає на сам
  проліт мосту і перетинає його; якщо встигнути знищити міст, поки танк ще
  на дорозі або на прольоті — очки потроюються, АЛЕ ТІЛЬКИ якщо він вже
  реально був на прольоті (`bridge.tankOnBridge === true`); сам танк при
  цьому НЕ гине, а "застрягає" й стріляє, як звичайний танк на березі
  (детально — нижче, розділ "Танк на мосту: дорога + застрягання").
- Бонусні "ЛГБТ повітряні кулі" (веселкові, з корзиною) з літерами:
  `T` triple-постріл (вперед+вліво+вправо, всі прямі), `M` missile
  (самонаведення з обох боків), `D` double (вдвічі частіші постріли),
  `F` fuel (миттєво 100%), `N` nuke (знищує всіх ворогів на екрані, але НЕ
  кулі), `X` extra life. Бонус діє до підбору іншого або до краху.
- Ліміт 3 вороги кожного типу на екрані одночасно.
- Швидкість рівня зростає на 10% з кожним пройденим мостом (лінійно,
  х2 на рівні 11).
- Береги річки плавні (не рвані): `TerrainGen` рухає `halfWidth`/`centerX`
  через "швидкість" (`halfVel`/`centerVel`, інерція з м'яким відбиттям від
  меж), а не незалежним випадковим кроком щорядка — дивись розділ про
  модель скролу вище.
- Дерева/кущі на берегах: `TerrainGen.nextRow()` кожного рядка окремо для
  лівого й правого берега має лічильник-"кулдаун" (`decoLeftCooldown`/
  `decoRightCooldown`), при досягненні нуля генерує `row.decoLeft`/
  `row.decoRight` (`{tree, inset, variant}`) і скидає кулдаун на випадкове
  число рядків (7-18). **Рендеряться НЕ через `Graphics`** (як було
  спочатку), а як готові PNG-іконки — окремі `Image`-об'єкти, що
  спавняться разом зі своїм рядком і рухаються зі скролом; на колізії
  через постріл гравця ВПЛИВАЮТЬ (їх можна знищити) — детально дивись
  два останні записи в "Історія фіч" нижче ("Дерева/кущі на березі стали
  знищуваними" і "Готові іконки для дерев/кущів").
- Заправки (`fuelTimer`) з'являються вдвічі частіше, ніж у першій версії:
  інтервал 2.75–4.25с замість 5.5–8.5с.
- Ігрове поле на всю висоту екрана: константа `H` більше не хардкод 640,
  а `Phaser.Math.Clamp(window.innerHeight, 640, 1400)` (дивись верх файлу).
  Все інше (`ROWS_COUNT`, `PLAYER_Y`, позиції HUD) вже виражені через `H`
  формулами, тому працює автоматично. Обчислюється один раз при завантаженні
  сторінки (не реагує на подальший resize вікна — це нормально для такого
  типу гри).
- Берегові танки тепер "заїжджають" до берега, а не з'являються одразу на
  ньому:
  - `spawnShoreTank()` стартує танк РІВНО на краю екрана (`x=0` зліва,
    `x=W` справа, залежно від `side`) і зберігає ПРЯМЕ посилання на "свій"
    рядок берега (`t.row = this.rows[3]`, фіксується один раз при спавні).
  - **Важливо:** `updateTanks()` навмисно НЕ шукає рядок через
    `rowAtScreenY(t.y)` щокадру — при від'ємному `y` (танк ще над екраном)
    ця функція клампиться на "поточний" `rows[0]`, який щокадру змінюється
    (нові рядки постійно `unshift`-яться), тож дерево, поставлене на
    "свій" рядок, могло взагалі не збігтися з тим, який танк перевіряє.
    Пряме посилання на об'єкт рядка вирішує це раз і назавжди — `row.left`/
    `row.right`/`row.decoLeft`/`row.decoRight` в ньому незмінні після
    створення.
  - Танк рухається до берега зі швидкістю `DRIVE_SPEED = 60` px/сек
    (`updateTanks()`). Якщо на "своєму" рядку є `decoLeft`/`decoRight` з
    `tree: true` і воно розташоване між краєм екрана і берегом (перевірка
    `treeX < bankX` для лівого боку / `treeX > bankX` для правого) — танк
    зупиняється за `TREE_CLEARANCE = 20` px до дерева і залишається там
    назавжди (кущі, `tree: false`, не блокують).
  - Стріляє (`fireTimer` рахується) ЛИШЕ коли `t.atBank === true`, тобто
    реально дістався справжньої лінії берега (`Math.abs(t.x - bankX) < 1`),
    а не зупинився перед деревом.
  - Постріли танків (`fireTankShell`) завжди суто горизонтальні: `vy: 0`,
    і `updateTankBullets()` не додає до `.y` жодного скролу — жодних
    відхилень немає й не повинно з'являтися.
- Текст програшу — `'ГРА ВСЬО'` (`GameScene.gameOver()`), НЕ "GAME OVER".
  Саме така форма (з великої, без крапки) — так просив користувач, не
  "виправляй" на англійський варіант.
- **Танк на мосту: дорога + застрягання.** `spawnBridgeVisual()` тепер
  стартує танк не на самому мосту, а на "дорозі" перед ним:
  `bridge.tankStartX` = позиція за `ROAD_LEN = 90` px до краю мосту
  (обрізана краєм екрана, якщо берег вузький), `bridge.tankEndX` —
  протилежний край прольоту, як і раніше. Рух — той самий
  `Phaser.Math.Linear(startX, endX, tankProgress)` на всю відстань
  (дорога + міст), швидкість `bridge.tankSpeed = 70` px/сек (піднята з 42,
  бо відстань зросла — інакше на високих рівнях танк не встигає доїхати
  до того, як усе проскролить за межі екрана).
  `bridge.tankOnBridge` (обчислюється щокадру в `updateBridgeVisuals()`
  як `x >= bridge.left`/`x <= bridge.right` залежно від напрямку)
  відрізняє фазу "ще їде дорогою" від "вже на прольоті" — це і є критерій
  для x3-бонусу.
  Якщо гравець влучає по мосту (`resolveMissileCollision()`, гілка
  "влучання по мосту") ПОКИ `bridge.tankAlive` ще true (танк не встиг
  втекти) — раніше танк просто вибухав разом з мостом; ТЕПЕР замість
  цього викликається `strandBridgeTank(bridge)`, яка перетворює його на
  звичайний запис у `this.tanks[]` (той самий масив, що й берегові танки):
  `row: null` (нікуди більше не їде — вже "запаркований"), `atBank: true`
  (стріляє одразу, щойно спрацює `fireTimer`), `side` виставляється так,
  щоб стріляти в напрямку, в якому він рухався (`tankDir === 1 → 'left'`,
  бо `side:'left'` в `fireTankShell()` означає постріл ВПРАВО). Завдяки
  цьому вся логіка стрільби/колізій/видалення застряглого танка — це та
  сама логіка, що й для звичайних берегових танків, без дублювання коду.
  `updateBridgeVisuals()` має свою власну (резервну) перевірку
  `if (!bridge.alive) this.strandBridgeTank(bridge)` на наступний кадр —
  це підстраховка на випадок, якщо колись з'явиться інший шлях знищення
  мосту, що не проходить через `resolveMissileCollision()`.
  **Важливо:** через це `updateTanks()` більше не може покладатись, що в
  усіх записів `this.tanks[]` є `t.row` — синхронізація `t.img.x/img.y`
  винесена ЗА межі `if (t.row) {...}` блоку (раніше застряглий танк без
  `row` мав "заморожений" спрайт, бо позиція оновлювалась лише всередині
  того блоку).

- **Готові іконки замість трьох процедурних спрайтів.** `tank`, `heli`,
  `balloon` тепер — реальні PNG-картинки (плоскі "емоджі-стиль" іконки),

- **Гелікоптер тепер стріляє по гравцю** (як в оригінальній River Raid,

  `updateTankBullets(dt)`. `nukeAllEnemies()` тепер прибирає й
  `heliBullets`, що вже в польоті.

  — напрямок (вліво/вправо) визначається один раз у момент пострілу залежно
  від того, з якого боку зараз `this.player` (`this.player.x >= e.x ? speed
  : -speed`). **Важлива історія:** спочатку тут була прицільна "ракета" під
  довільним кутом (вектор від гелікоптера до поточної позиції гравця, з
  вертикальною складовою) — користувач прямо попросив це прибрати, бо це
  надто ускладнювало гру й не відповідало оригіналу. Якщо колись знову
  захочеться "покращити" AI гелікоптера прицілюванням по вертикалі —
  спершу запитай, це свідоме рішення, а не недогляд.
- **Дерева/кущі на березі стали знищуваними.** Раніше `row.decoLeft`/

  танк наступного кадру продовжить їхати до берега, бо перевіряє
  `row.decoLeft`/`row.decoRight` щокадру, а не одноразово при спавні.

- **Анімований вибух + перехід іконок з base64 на окремі файли в
  `assets/`.** Дві пов'язані зміни в одному заході.
  - *Вибух:* замість трьох процедурних текстур `explo1/2/3`, які
    підмінялись одна одною для ефекту "росту" (кругла анімація), тепер одна
    PNG-іконка `explo` (48x48, готова картинка користувача). Анімацію
    робить не зміна текстури, а `spawnExplosion(x, y)`/`updateExplosions(dt)`:
    кожен вибух — запис `{img, t}` у `this.explosions[]`, `t` рахується від
    0 до `EXPLO_DURATION` (0.4с). Перша половина (`frac < 0.5`) —
    `setScale()` росте від `EXPLO_START_SCALE` (0.15) до `EXPLO_PEAK_SCALE`
    (1), друга половина — так само плавно назад до 0.15 (лінійна
    інтерполяція через `growFrac`, симетрична навколо середини). Паралельно,
    весь час анімації, `img.angle = EXPLO_ROTATION_SPEED * ex.t`
    (`EXPLO_ROTATION_SPEED = 900`, тобто рівно один повний оберт за 0.4с) —
    позитивний `.angle` в Phaser це ЗАВЖДИ обертання за годинниковою
    стрілкою (перевірено окремо скриншотами), так що напряму задавати
    від'ємну швидкість НЕ треба, якщо колись захочеться "проти годинникової"
    — просто зроби `EXPLO_ROTATION_SPEED` від'ємним.
    **Гочка для тестів:** Phaser сам нормалізує `.angle` в діапазон
    `(-180, 180]`, тож при читанні `.angle` під час монотонно зростаючого
    `t` значення "загортаються" (напр. 190° читається як -170°) — це НЕ баг
    відображення (візуально обертання плавне й безперервне), а особливість
    getter'а. Якщо пишеш тест на монотонність кута — порівнюй НЕ самі
    значення, а найкоротшу "загорнуту" різницю між сусідніми замірами:
    `((rawDelta + 540) % 360) - 180`, і перевіряй що вона стабільно
    позитивна (для годинникового напрямку).
  - *База64 → окремі файли:* усі 8 готових іконок (`tank`/`heli`/`balloon`/
    `player`/`jet`/`ship`/`fuel`/`explo`) перестали бути base64-константами
    в `game.js` і стали звичайними файлами `assets/*.png`, кожен заздалегідь
    відмасштабований (LANCZOS) рівно до розміру показу в грі (без
    3x-суперсемплінгу, яким рятувались раніше) — сумарно ~50 КБ замість
    100+ КБ роздутого тексту в `game.js`. Свідома ціна: гра й тести більше
    не працюють через `file://`, обов'язково потрібен http-сервер (`npm
    start` для гри, `tests/serve.js` для тестів — деталі в розділах 4 і
    "Тести" вище). `.gitignore` більше НЕ виключає `*.png` — раніше PNG в
    `assets/` були просто довідковими копіями (гра їх не читала), тепер це
    обов'язкові рантайм-файли, які мають бути закомічені в git.
- **Готові іконки для дерев/кущів + перехід на Image-об'єкти (більше не
  Graphics щокадру).** `tree1`/`tree2` (два варіанти дерева) і
  `bush1`/`bush2` (два варіанти куща) — готові PNG-іконки з `assets/`,
  той самий підхід, що й для решти спрайтів (константи `DECO_TREE_KEYS`/
  `DECO_BUSH_KEYS` одразу після `EXPLO_*`-констант на початку файлу).
  `row.decoLeft`/`row.decoRight` отримали нове поле `variant` (0 або 1,
  `Phaser.Math.Between(0,1)` у `TerrainGen.nextRow()`) — який саме з двох
  PNG свого типу показати; сам `tree`-boolean і далі визначає геймплей
  (очки/блокування танка), `variant` — суто візуальна різноманітність.
  **Архітектурна зміна вища за просто "заміну картинки":** раніше
  дерево/кущ малювалось напряму примітивами (`drawTree`/`drawBush`,
  `g.fillCircle`/`g.fillRect`) у `drawTerrain()` щокадру наново — цей
  підхід більше НЕ годиться для растрових PNG, бо `Graphics` вміє малювати
  лише прямокутники/кола/лінії, не картинки. Тому дерева/кущі тепер — це
  окремі `Image`-об'єкти, керовані трьома новими методами `GameScene`:
  - `spawnDecoImages(row, y)` — створює `Image` для `row.decoLeft`/
    `row.decoRight`, якщо вони є, і кладе посилання прямо в дані рядка
    (`row.decoLeft.img = ...`). Викликається двічі: один раз для КОЖНОГО з
    початкових рядків одразу після заповнення `this.rows` у `create()`
    (`y = i*ROW_H`, бо `scrollAccum === 0` на той момент), і один раз для
    щойно згенерованого рядка одразу після `this.rows.unshift(newRow)` у
    скрол-циклі (`y = this.scrollAccum` — щойно відняли `ROW_H`, новий
    рядок сидить на позиції індексу 0, тож формула `i*ROW_H+scrollAccum`
    дає рівно `scrollAccum`).
  - `updateDecoImages(scrollDelta)` — викликається щокадру в
    `updatePlaying()` поруч з `updateBridgeVisuals`; для кожного рядка з
    `decoLeft.img`/`decoRight.img` додає `scrollDelta` до `.y`. Той самий
    підхід, що й для fuel/tanks/balloons/bridge (неперервний рух
    `entity.y += scrollDelta`), а НЕ перерахунок з індексу рядка щокадру —
    саме тому `.x` дерева/куща обчислюється ОДИН РАЗ при спавні
    (`row.left - inset` / `row.right + inset`) і більше ніколи не
    змінюється, бо `row.left`/`row.right` для вже створеного рядка
    незмінні назавжди.
  - `destroyRowDecoImages(row)` — знищує `Image`-об'єкти рядка, що
    вислизнув за нижній край `this.rows` (`this.rows.pop()` у скрол-циклі,
    ПЕРЕД тим, як рядок остаточно викидається) — якщо дерево там ще живе
    (гравець не встиг підстрелити), інакше лишився б "осиротілий" `Image`,
    що ніколи не видаляється (memory leak).
  `destroyDeco()` (постріл гравця) тепер ТЕЖ знищує `row[key].img` перед
  тим, як занулити `row[key]` — раніше просто занулював дані, а
  `drawTerrain()` сам переставав малювати той рядок на наступному кадрі;
  тепер, коли рендер — не перемальовування з нуля, а живий `Image`-об'єкт,
  забути його знищити означало б лишити картинку "висіти" в сцені назавжди.
  Радіуси влучання в `resolveMissileCollision()` розширено з 9/8px до
  16/14px (дерево/кущ) — старі числа були підігнані під крихітні
  Graphics-кружечки (~14-19px), нові PNG помітно більші (~29-34px дерево,
  ~28px кущ), тож і зона влучання має бути відповідно щедрішою, інакше
  гравцю здавалося б, що постріл "проходить крізь" видиму картинку.
  Глибина рендеру (`setDepth(3)`) обрана між землею (`terrainGfx`, depth 0)
  і береговими танками (depth 4) — дерева/кущі мають бути над ґрунтом, але
  під транспортом.
- **Лічильник HOMING-ракет + хітбокси по масці PNG (замість прямокутників).**
  Дві незалежні зміни в одному заході.

    одна подія SPACE, а не кожна з двох випущених ракет) і сам вимикає
    `activePower` при досягненні нуля. `collectBalloon()` для `'M'` тепер
    гілка сама по собі (була частиною спільної гілки з T/D): додає 50 до
    наявного лічильника, якщо бонус вже активний і не вичерпаний, інакше

  - *Хітбокси по масці:* див. окремий розділ "Хітбокси по масці PNG
    (`pixelHit`, `SPRITE_MASKS`)" вище. Замінює точкові прямокутникові
    перевірки в `resolveMissileCollision()` для ворогів/заправки/танків/
    дерев-кущів/куль-бонусів/танка на мосту. **Це РОБИТЬ ЗАСТАРІЛИМИ** числа
    16/14px з попереднього запису "Готові іконки для дерев/кущів" вище — ті
    константи для дерева/куща в коді більше НЕ існують, замінені на
    `pixelHit(row.decoLeft.img, mx, my)`. Якщо десь у діффі знову з'явиться
    `Math.abs(mx - x) < N` для однієї з цих сутностей — це відкат, а не
    покращення.

  колізії; якщо додаєш новий елемент — звіряй `getBounds()` із сусідніми
  (є готовий приклад у тесті, п.11).
  Заразом: `'PRESS SPACE TO START'` → `'НАТИСНІТЬ ПРОБІЛ ДЛЯ ПОЧАТКУ'`
  (переклад, свідомо без крапки, у стилі решти написів гри), і під нею
  додано `` `v${GAME_VERSION} by Alex Raven` `` — перший в проєкті випадок
  явного номера версії десь у грі (раніше версій не було взагалі, лише
  `CHANGELOG.md` без нумерації).
- **Готова іконка для ракети самонаведення.** `spawnHomingMissile()` тепер
  малює `'homingMissile'` (готова PNG-іконка, 6x32, `HOMING_MISSILE_SCALE`)
  замість спільної процедурної текстури `'missile'`, яку й далі
  використовують звичайний і потрійний постріл (`spawnMissile()` не
  чіпали — заміна свідомо торкнулась ЛИШЕ самонавідних ракет, за прямим
  проханням "заміни зображення ракет з самонаведенням"). Джерело —
  вертикальний малюнок ракети з полум'ям, дуже витягнутий (нативне
  співвідношення сторін ~1:6.8); щоб не робити спрайт неприродно довгим
  відносно решти іконок гри (танк/гелікоптер — 24-30px заввишки), фінальний
  розмір підібрано під висоту, близьку до старої `missile`-текстури (24px),
  трохи більшу (32px) заради деталізації, а не під повне збереження
  оригінального співвідношення сторін — звідси й неширокий (6px) результат.
  Ніс дивиться вгору за замовчуванням, як і стара текстура, тож формула
  повороту (`img.rotation = Math.atan2(vy, vx) + Math.PI / 2`, і в
  `spawnHomingMissile()`, і в `updateMissiles()` для самонаведення в
  польоті) лишилась без змін.

## Наступні кроки / формат роботи

Коли я прошу нову фічу чи фікс:
1. Зроби зміну в `game.js` (і `game.css`/`index.html`, якщо треба).
2. Прожени `npm test` — усі тести мають бути зеленими.
3. Якщо додав нову механіку — додай тест під неї.
4. Додай запис у `CHANGELOG.md` (найновіше зверху).
5. Онови `GAME_VERSION` на початку `game.js` (видно на тайтл-екрані як
   `vX.Y by Alex Raven`) — бампни мінорну цифру для звичайної зміни/фічі.
6. Коротко опиши, що змінилось, українською.

Гру НЕ потрібно знову "зшивати" в один HTML-файл — тримаємо `index.html`,
`game.css`, `game.js`, `phaser.min.js` окремими файлами.
